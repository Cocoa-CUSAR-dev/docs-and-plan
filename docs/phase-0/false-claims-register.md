# Documented Claims vs. Code Reality

Every entry below is a claim made in the **final report** that does **not** hold up against the actual code — verified directly this session, not inferred. Each row cites the exact section and quoted text from the report, and the exact code (file, line) that contradicts it, so anyone on the team can re-check it independently in under a minute. (Two other claim/code mismatches were found in the team's own supplementary analysis docs, not the final report itself — those are tracked separately in [Flutter App Technical Analysis](/docs/phase-0/flutter-analysis) and [Go Server Walkthrough](/docs/phase-0/go-server-walkthrough), not listed here.)

:::warning[The two "final report" files in the repo are different drafts]
`static/files/reports/final-report.docx` and `static/files/reports/final-report.pdf` are **not the same document**. The docx contains the full UX-iteration narrative (§4.1.1–4.1.5: prototype → Chiang Mai testing → dynamic forms → Prachuap beta → entity-centric revision). The PDF's own §4.1 ("Development process," page 24) is entirely different content — backend API documentation, no UX narrative at all. **Section numbers below refer to `final-report.docx`** — page numbers aren't cited because they aren't stable between the two files (and page position depends on the reader's own rendering anyway); section number + exact quote is the reliable, Ctrl-F-able identifier.
:::

## Why this matters

Claims 1 and 5 are the same underlying gap (the dynamic form engine doesn't actually reach the mobile app) proven two different ways — §4.1.3's prose claim, and Table 6.1's own claimed-and-passed test case. Together they're the single biggest finding from the whole Phase 0 review — see the [headline finding](/docs/plans/architecture-session-notes#headline-finding) in the Architecture Review recap. Claims 2–4 show the report describing features (OTP, tree-level tracking, snapshot logging) that read as genuine intent but were never built. Claims 6–7 matter specifically for the new work: if anyone assumes the old system's infrastructure is elastic or encrypted-by-default when planning where the new chatbot service or its traffic to Go/Kotlin lands, that assumption is wrong — see [ADR 0007](/docs/adr/deployment-and-hosting) (hosting, still pending) and [ADR 0001](/docs/adr/old-new-integration-seam) (the seam the new service calls into).

None of this is about blaming the previous team — normal for a fast-moving student project where docs drift from code. It matters now because the new architecture work (see the [ADRs](/docs/adr)) makes decisions that depend on knowing which parts of the old system are real.

:::danger[Separate, more urgent finding — not a "false claim," an active exposure]
While searching for infrastructure config, `go-server-transfer-2026-06-16/docker-compose.yml` was found to contain a **live-looking NeonDB password and JWT signing key in plaintext**, committed directly in the file. This is unrelated to documentation accuracy but far more urgent — if this ever reached a public or shared git history, both should be rotated immediately. The `web-backend` README already carries a general warning about this ("Rotate the NeonDB password and JWT_KEY if there's any chance they were exposed in the old transfer folder") — this is a concrete instance of exactly that risk, found in the transfer folder itself.
:::
